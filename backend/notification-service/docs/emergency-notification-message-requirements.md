# Emergency Notification Message Requirements

## 1. Purpose

This document defines the content, priority and safety requirements for emergency notifications generated by the Phoenix backend. It covers SMS alerts and real-time notifications displayed through web or mobile applications.

The purpose is to ensure that emergency messages are clear, accurate, timely and useful. This document provides requirements for future backend implementation; it does not implement SMS delivery.

## 2. Existing Backend Context

The current Phoenix notification event contains:

- `eventId`
- `eventType`
- `title`
- `message`
- `occurredAt`
- `metadata`

Stored notifications also contain:

- `id`
- `userId`
- `eventId`
- `eventType`
- `title`
- `message`
- `metadata`
- `isRead`
- `readAt`
- `createdAt`
- `updatedAt`
- `deletedAt`

The current data-ingestion implementation generates a critical hazard notification when `hazard_severity` is at least `0.8`. It generates a critical cyber-threat notification when the provided severity is `critical`.

The existing notification structure provides a useful starting point. However, emergency notifications also require a consistent priority, location, recommended action, issuing authority, expiry time and update information.

## 3. Priority Requirements

### 3.1 Critical

A critical notification describes an immediate or life-threatening situation requiring urgent action.

Requirements:

- Deliver immediately through every available channel.
- Clearly use the word `CRITICAL`.
- State the hazard or threat.
- Identify the affected location.
- Provide a direct action such as evacuate, avoid, disconnect or seek shelter.
- Include the issue time and expiry time.
- Identify the authority or trusted source.
- Do not delay delivery because of optional missing information.
- Continue issuing updates until the event is resolved.
- Prevent duplicate delivery of the same event to the same user.

Example events include severe bushfires, dangerous floods, active security incidents and critical cyber threats.

### 3.2 High

A high-priority notification describes a serious situation that may become critical or requires prompt preparation.

Requirements:

- Deliver promptly through the real-time channel.
- Use SMS when configured for the affected users or region.
- Clearly identify the threat and affected area.
- Explain what the recipient should prepare or avoid.
- Include issue time, source and an update link where available.
- Upgrade the notification if the severity increases.
- Expire or replace the notification when newer information becomes available.

### 3.3 Normal

A normal notification provides awareness or general information without requiring immediate emergency action.

Requirements:

- Deliver through the real-time application channel.
- Do not use alarming language.
- Explain the event and any optional precaution.
- Avoid unnecessary SMS delivery.
- Include a creation time and source.
- Allow the user to mark the notification as read.

## 4. Required Message Fields

| Field | Required | Purpose |
|---|---:|---|
| `eventId` | Yes | Uniquely identifies the source event and prevents duplicates. |
| `eventType` | Yes | Identifies whether the event is a hazard, cyber threat or system event. |
| `priority` | Yes | Must be `critical`, `high` or `normal`. |
| `title` | Yes | Provides a short description of the emergency. |
| `message` | Yes | Explains the event in plain language. |
| `recommendedAction` | Yes for critical/high | Tells the recipient what to do. |
| `location` | Yes for location-based hazards | Identifies the affected area. |
| `occurredAt` | Yes | Records when the event happened. |
| `issuedAt` | Yes | Records when the notification was created. |
| `expiresAt` | Yes for temporary alerts | Prevents outdated alerts from being presented as current. |
| `source` | Yes | Identifies the system, organisation or authority that issued the information. |
| `recipient` or `audience` | Yes | Identifies the user, group or affected region. |
| `channel` | Yes | Indicates SMS, real-time application, or both. |
| `status` | Yes | Indicates active, updated, resolved or cancelled. |
| `updateUrl` | Optional | Provides trusted additional information. |
| `metadata` | Optional | Stores structured event-specific information. |

The backend should reject a critical or high notification if its message, priority, source, timestamp or recipient information is missing. A location-based emergency should also require a valid location.

## 5. Plain-Language Rules

Emergency messages must:

- Begin with the priority and event type.
- Use short and direct sentences.
- Use familiar words instead of technical terminology.
- Tell the recipient exactly what action to take.
- Put the most important instruction first.
- Use an active voice, such as “Leave the area now.”
- State a specific location instead of phrases such as “nearby”.
- Include a clear date or time when timing matters.
- Avoid jokes, promotional language and unnecessary detail.
- Avoid uncertain instructions such as “possibly evacuate”.
- Avoid unexplained abbreviations.
- Avoid displaying internal IDs, stack traces or system errors.
- Include only links belonging to an approved or trusted domain.
- Separate verified information from information that is still uncertain.

The backend must not invent missing emergency information. If essential information is unavailable, the event should be rejected, quarantined for review or delivered using an approved fallback message.

## 6. SMS Requirements and Length Guidance

SMS messages must contain only the most important information:

1. Priority
2. Hazard or threat
3. Location
4. Required action
5. Trusted source or short update link

A single standard GSM-encoded SMS normally supports up to 160 characters. Messages containing Unicode characters may have a smaller single-message limit. Long or concatenated messages may be divided into multiple segments.

Phoenix should aim to keep emergency SMS content within 160 characters where possible. The backend must calculate the encoded message length rather than relying only on JavaScript character count.

Important safety information must not be removed simply to meet the preferred length. If the complete message cannot fit safely:

- Keep the action and location in the first segment.
- Remove unnecessary descriptive words.
- Use an approved short link for extra details.
- Do not shorten words in a way that creates ambiguity.
- Do not split a location, instruction or link incorrectly.
- Record the number of SMS segments before delivery.

## 7. Real-Time Application Requirements

Real-time notifications may contain more detail than SMS. They should include:

- Priority indicator
- Complete title and message
- Affected location
- Recommended action
- Issue and expiry time
- Source or authority
- Event status
- Map or structured metadata when available
- Trusted update link
- Read/unread status

Real-time notifications should support updates. A newer message for the same `eventId` should update or supersede the old notification instead of creating confusing duplicates.

Expired, cancelled or resolved notifications must be visually and technically distinguishable from active alerts.

## 8. SMS and Real-Time Comparison

| Requirement | SMS | Real-time application |
|---|---|---|
| Length | Short; preferably one segment | May contain additional detail |
| Critical action | Required | Required |
| Location | Short but specific | Detailed location or map |
| Metadata | Not displayed directly | May be displayed in structured form |
| Links | One approved short link | Full trusted update link |
| Updates | New SMS only when important | Can update existing notification |
| Read status | Usually unavailable | Supported |
| Formatting | Plain text | Structured title, body and actions |
| Delivery use | Critical and selected high alerts | Critical, high and normal alerts |

## 9. Missing or Unsafe Data Cases

The backend must detect the following cases:

- Missing `eventId`
- Missing or unsupported priority
- Empty title or message
- Critical/high alert without a recommended action
- Location-based alert without a location
- Invalid `occurredAt`, `issuedAt` or `expiresAt`
- Expiry time earlier than issue time
- Notification already expired
- Unknown or untrusted source
- Missing recipient or audience
- Unsupported delivery channel
- Duplicate `eventId` for the same recipient
- Raw personal data included unnecessarily
- Raw API keys, authentication tokens or passwords in the message
- Internal database errors or stack traces exposed to users
- Unapproved or malformed links
- Contradictory title and body
- Severity in metadata conflicting with the notification priority
- Message claiming an event is resolved while its status is active
- SMS exceeding the approved segment limit without review
- Unsupported characters causing unexpected SMS segmentation

A rejected event should be logged using its safe event identifier and validation reason. Sensitive message content should not be unnecessarily copied into logs.

## 10. Message Examples

### 10.1 SMS Example

> CRITICAL FLOOD—Werribee River area. Move to higher ground now. Avoid flooded roads. Updates: [approved link]

This example identifies the priority, threat, location and immediate action without unnecessary technical information.

### 10.2 Real-Time Message Example

**Title:** Critical Flood Warning — Werribee River Area

**Priority:** Critical

**Message:** A dangerous flood has been detected near the Werribee River. Move to higher ground immediately and do not enter flooded roads.

**Recommended action:** Leave low-lying areas and follow emergency-service instructions.

**Location:** Werribee River and surrounding low-lying areas

**Status:** Active

**Source:** Approved emergency authority

**Issued:** 8 September 2026, 4:30 PM AEST

**Expires:** 8 September 2026, 8:30 PM AEST

**Updates:** [approved link]

## 11. Future Implementation Checklist

Before an emergency-notification feature is accepted, confirm that:

- [ ] `eventId` is present and valid.
- [ ] Event type is supported.
- [ ] Priority is critical, high or normal.
- [ ] Title and message are not empty.
- [ ] Critical/high alerts contain a recommended action.
- [ ] Location is provided for location-based emergencies.
- [ ] Source or authority is approved.
- [ ] Recipient or audience is defined.
- [ ] Issue and occurrence timestamps are valid.
- [ ] Expiry time is valid and later than issue time.
- [ ] Delivery channel is supported.
- [ ] SMS encoded length and segment count are checked.
- [ ] Critical details appear in the first SMS segment.
- [ ] Links use approved domains.
- [ ] Sensitive information is excluded.
- [ ] Duplicate event delivery is prevented.
- [ ] Updated, resolved and cancelled states are supported.
- [ ] Validation failures are logged safely.
- [ ] SMS and real-time examples pass automated tests.
- [ ] Message delivery failure and retry behaviour are defined.

## 12. Current Backend Gaps

The current Phoenix backend does not consistently expose:

- Explicit `priority`
- `recommendedAction`
- `location`
- `issuedAt`
- `expiresAt`
- `source`
- `audience`
- `channel`
- `status`
- `updateUrl`

The current critical hazard and cyber-threat publishers create useful titles and messages, but the recommended action is not a dedicated field. Hazard notifications include location inside metadata and message text, while cyber notifications may not identify an affected audience or action.

The existing proto also exposes only `id`, `title`, `body` and `recipient`. Future implementation should align the proto, TypeScript interfaces, database model and RabbitMQ event contract.

## 13. Scope and Recommendations

This task defines requirements for future implementation. It does not change the existing notification API, database schema, RabbitMQ publisher or delivery service.

The recommended next implementation step is to agree on one shared emergency-notification contract and then update:

1. RabbitMQ notification events
2. Notification validation
3. Database model and migration
4. gRPC proto
5. API Gateway interfaces
6. SMS formatting logic
7. Real-time notification responses
8. Automated tests
